# Design and Review method relationship

## Decision

Keep the skill descriptions:

- **Design scientific software before implementation**
- **Review scientific software after implementation**

Each skill accepts one natural-language request. They share one Scientific Kernel and canonical identities while
preserving different tense, authority, ordering, and conclusions.

## Method relationship

| Stable scientific content | Design before implementation | Review after implementation | Required separation |
|---|---|---|---|
| Authority and regime | Design Frame freezes requested change, constraints, and owner decisions | Scope seals actual target, authority, regimes, and evidence | Design authority is intent; Review facts need fresh bases. |
| Scientific Map | Prospective Map defines intended objects, CLM, and COR | Observed Map records what frozen bytes supply | Preserve identities; re-observe epistemic states. |
| Five Dimensions | Projections return obligations, alternatives, decisions, proposals, or UNK | Audits return calibrated verdicts, findings, and UNK | Design cannot issue an implementation verdict; Review cannot invent owner authority. |
| Evidence | EVD plan states what could challenge CLM/COR | EVD result or UNK states what was observed or blocked | A plan is not an observation; same-path evidence is not automatically independent. |
| Ownership | Owner decision selects meaning, regime, method, lifecycle, evidence, or Module shape | Located authority or UNK limits interpretation | Review may propose repair but cannot invent intent. |
| Change | Implementation sequence and change checks bound prospective propagation | Located consequence and successor Scope record actual drift | Material change reopens Review; changed Frame reopens all five Projections. |
| Run result | Delivered Design may retain blocking owner decisions | Delivered Review may contain UNPROVEN | Delivery, readiness, and verdict are separate. |
| Run Summary | Reports persisted artifact paths, assessed readiness or NOT_ASSESSED, assurance, and material Open Items | Reports assessed target and coverage, persisted paths and available Scope digest, accepted verdicts, and a consequential FAIL Finding when present | The summary projects the established results and locates full records. |
| Open Item | Projects one UNK, owner Decision, or Blocker with independent delivery and implementation blocking values | Projects the same three kinds without changing a verdict | Preserve source identity and kind; never merge scientific, authority, and delivery meanings. |
| Use Record | Projects intended use, inputs, settings, evidence plan, limits, responsibility, and triggers | Projects actual inputs, settings, evidence, limits, responsibility, and triggers | It references the Map and Run record; it does not create new facts. |
| Reflexive use | Design may define a successor SSRE2 version | Review may audit frozen SSRE2 bytes | Current output stays outside target; self-support is not independent evidence. |

This table is a development oracle, not automatic runtime text. The Kernel owns the compact rule: Design Frame
becomes sealed Scope, prospective identities become observed identities, EVD plans become EVD results or UNK,
material IDs persist, and scientific support is never inherited.

## Wording rules

1. Use the canonical terms in [SSRE2 Language](../../../GLOSSARY.md).
2. Use method-specific verbs: Design defines, requires, proposes, and plans; Review seals, observes, challenges,
   audits, and reports.
3. Preserve time and evidence asymmetry.
4. Keep outputs distinct: SSRE2-DESIGN.md, SSRE2-SCOPE.md, and SSRE2-REVIEW.md.
5. Keep the Run Summary minimal; locate full records in artifacts.
6. Keep Open Items and Use Record fields as projections, not caller requirements or duplicate fact tables.
7. Test extra runtime wording by ablation; it earns context only if it prevents a measured identity, authority,
   evidence, blocker-disclosure, or reflexive-closure failure.

## Run Summary controls

Run each case independently and grade the visible handoff against the underlying records.

| Controller input | Expected Run Summary |
|---|---|
| Give Design a complete brief and allow all five Projections, the architecture assessment, and artifact delivery to finish. Resolve all implementation-blocking decisions. | DELIVERED and READY, with the actual report path. A variant with a fully assessed blocking owner Decision stays DELIVERED and reports BLOCKED with the decision owner and required action. |
| Stop Design before its readiness assessment, with no implementation-blocking Open Items yet recorded. | INCOMPLETE and NOT_ASSESSED, with the skipped work and its closing path. |
| Fail the Design report write after a valid READY assessment and a resolved Artifact Route. | INCOMPLETE and READY, with the write blocker, paths limited to persisted artifacts, and the unavailable Use Record and runtime provenance supplied inline. |
| Invoke Review without a pin. Include a relevant working-tree edit and an unrelated one. Repeat with an explicit revision of the same target. | The default run identifies the requested coverage and the exact selected working-tree content. The pinned run identifies the revision and its distinct file content. Each summary reports which working-tree changes were included. |
| Seal the Review Scope, then omit an Audit or return one for a different digest. | INCOMPLETE. Report only accepted verdicts for the current Scope and use a delivery-blocking Open Item for the missing Audit. List only persisted artifact paths. |
| Complete all five Audits with a material FAIL supported by an existing Finding and no unresolved items. | DELIVERED. Report the verdict and a consequential Finding with its locator even when the Open Items list is empty. |

## Current assessment

The one-request Interface and one-Kernel/two-method shape are structurally coherent. Material risks are behavioral:
a model may carry Design bases into Review, use self-produced support as independent EVD, omit CLM/COR on an
unchanged target, hide a blocker, merge unlike Open Items, duplicate the Scientific Map inside Run Summary or Use
Record, or let a proposal become owner authority.

Those failures require paired handoffs, blocker injection, and reflexive blind replay on pinned targets.
